# Backend architecture: Database management (SQL, document, key-value)

> [Index](../README.md) · **Use for:** repositories, unit of work, PostgreSQL + Alembic, MongoDB indexes/migrations, Redis as storage. Placeholders are defined in the index.
> **Related:** [data-stores](../aws-infrastructure/services/data-stores.md)

## 6. Persistence

### 6.1 Repository pattern (independent of technology)

- One repository per aggregate. Its methods use business language (`get_for_owner`,
  `append_message`) and avoid generic CRUD wherever possible.
- **Ownership and tenancy filters live inside the repository's queries**
  (`owner_id = :user`). Never filter after fetching.
- Transactions: a service that must change several things atomically uses a **unit of work**
  port (`async with uow: ...; await uow.commit()`). Repositories never commit on their own.
- Every list endpoint is paginated, cursor-based by default (`?cursor=…&limit=…`), with a
  server-side maximum on `limit`.
- IDs are UUIDs (v7 if it is available, because they sort by time), generated by the
  application, not by the database. Timestamps are timezone-aware UTC.

### 6.2 SQL (PostgreSQL)

- `infrastructure/db/sql.py` owns the async engine (`pool_pre_ping=True`) and an
  `async_sessionmaker(expire_on_commit=False)`.
- ORM models live in the adapter, or in `infrastructure/db/models/` if several features share
  tables. They share an abstract base with `id`, `created_at` and `updated_at`.
- **Alembic**:
  - The URL comes from the settings in `migrations/env.py`, never from `alembic.ini`.
  - `env.py` imports all models once.
  - Each migration file is named `NNNN_<slug>.py`, and every migration has a working
    `downgrade()`.
  - A test runs upgrade, downgrade and upgrade again on a throwaway database.
- Migrations run as a separate one-shot process (`migrate` service or job). The app never
  runs them on import or at startup.

### 6.3 Document store (MongoDB)

- `infrastructure/db/mongo.py` owns one client per process (`AsyncMongoClient` or Motor),
  exposes the database handle, and closes the client on shutdown.
- **Indexes are declared in code**, for example `INDEXES = {"conversations": [IndexModel([("owner_id", 1), ("updated_at", -1)])]}`,
  and applied idempotently by the `migrate` process (or at startup in dev). Every query
  pattern has an index that supports it.
- Every document carries `schema_version: int`. Old documents are upgraded lazily on read,
  with a write-back, or by a numbered migration script under `migrations/mongo/NNNN_<slug>.py`.
  The migration runner records which scripts have been applied in a `_migrations` collection.
- Validate data at the boundary with Pydantic. Optionally add a `$jsonSchema` validator on the
  collection for critical invariants.
- Never let a document grow without bound. Store one message per document, with
  `conversation_id` and an index on it. Do not append an unbounded array to a single
  conversation document, because MongoDB caps documents at 16 MB.
- Use `w="majority"` writes for data that must not be lost. Use multi-document transactions
  only when they are really needed; they require a replica set (dev:
  `--replSet rs0` with a one-off init).

### 6.4 Key-value (Redis) as storage

Use Redis for derived or ephemeral state only: caches, sessions, rate-limit counters, locks,
short-lived job state. Never make Redis the only copy of anything that must survive. If data
must be durable, its system of record is a database.
